03

合约底层逻辑 · 提炼

从整个准备过程里提炼的合约核心逻辑,⭐ 是高频必懂。这节是知识,第 06 节机制问答是怎么答,配套看。

A · 杠杆与保证金

⭐ 杠杆的本质

杠杆 = 名义价值 ÷ 保证金(20x = 5% 保证金)。放大的是本金的回报率和风险率,不是盈亏绝对值 —— 绝对盈亏只由"仓位大小 × 价格变动"决定;仓位放大 20x,盈亏不会被"除以 20",而是整个仓位的盈亏都落到你那点本金上。

维持保证金率(MMR)

维持仓位所需的最低保证金比例,数值很小(0.4%~0.7%),且分档 —— 仓位越大要求越高。

⭐ 保证金率(健康度)vs MMR(最易混)

保证金率 = 账户权益 ÷ 维持保证金,通常 >100%、越高越安全、跌到 100% 强平。判断法:任何 >100% 的数(120%、212%)绝不是 MMR,而是健康度;MMR 永远是那个很小的费率。

⭐ 全仓 vs 逐仓:保证金到底怎么算

逐仓:你给这个仓位单独划一份保证金,亏损只吃这份钱 —— 浮亏再大也不碰账户里其他资金,爆了就是这份保证金归零,最大亏损 = 该仓保证金(可控);想撑住可以手动追加。全仓:整个账户可用余额 + 所有全仓仓位的未实现盈亏,共同作为一个保证金池 —— 某个仓浮亏时,账户里的其他钱会自动填进去撑住它;而且一个仓的浮盈可以给另一个仓当保证金(盈亏互抵),这是对冲组合必须用全仓的原因。

强平价差异 · 一个算例

账户 1000U,拿 100U 开 10x 多单。逐仓:只有这 100U 兜底,价格跌约 9% 出头(亏掉 100U − 维持保证金)就强平,账户里另外 900U 毫发无损。全仓:整个 1000U 都在兜底,要跌到把 1000U 权益逼近维持保证金才强平 —— 强平价远得多、更抗波动,但爆一次亏的是 1000U 不是 100U,且同方向的其他全仓仓位可能被连环平掉。一句话:逐仓是"止损前置",全仓是"用整个账户换生存时间"。

谁该用哪个

逐仓:方向性投机、高杠杆短线、想严格控制单笔风险 —— 亏损上限在开仓那一刻就锁死了。全仓:对冲/双向组合(多空两腿盈亏互抵,单边波动不容易被误强平)、愿意主动盯保证金的老手。所以产品上新手默认逐仓是行业共识 —— 默认全仓等于让新手拿全部余额给一笔单兜底。

⭐ 切换时的产品设计(最见功力)

有持仓时切换模式,强平价和最大亏损当场就变 —— 逐仓切全仓,强平价变远但风险敞口从一份保证金变成全账户;全仓切逐仓反过来,强平价可能瞬间贴脸。所以必须:①弹确认并直接展示"切换前 vs 切换后"的强平价对比,让用户看后果做选择,而不是记名词;②逐仓的追加保证金入口放在持仓卡上随手可点;③双向持仓下多空两腿保证金是共享还是独立,口径必须页面说清。这类切换口径出错,和强平价口径一样是资损级问题。

B · 价格与盈亏

⭐ 标记价 vs 最新成交价

成交 / 委托用最新价;算未实现盈亏和触发强平用标记价(= 指数价[多所现货加权] + 合理基差)。标记价更平滑公允,防插针。用户困惑"没到我看的价怎么爆了"就源于此。

未实现盈亏

=(现价 − 开仓价)× 数量 × 方向(U 本位线性)。

C · 资金费率

⭐ 本质:锚定价格,不是手续费

把永续价格锚定到现货指数价;多空之间互付,平台不收。溢价 → 正费率 → 多付空 → 压溢价回落。(订单簿型 CEX 平台其实没有方向敞口 —— 多空撮合永远相等,所以资金费率不是"平台对冲手段"。)

构成 · 结算 · "被偷袭"

≈ 溢价指数 + clamp(利率 − 溢价, ±上限);每 8h 结算,只在结算时刻持仓才付 / 收,提前平不付。用户结算前几分钟开仓被扣一笔、以为乱收费 → 所以要显眼展示结算倒计时。

D · 强平链路(最核心,最常被深挖)

⭐ 触发

保证金率跌到维持线(按标记价)。

⭐ 强平价 vs 破产价

强平价在破产价之前,中间那段是缓冲(强平费 + 滑点余量);破产价 = 本金正好亏光的价。

⭐ 接管"没收"的是缓冲,不是本金

被强平时,本金大头是被价格下跌的浮亏真实亏掉的;引擎接管时"没收"的,只是触发那一刻剩下的那一小笔缓冲(≈维持保证金)。有完好本金就不会被强平 —— 强平只在权益逼近维持保证金时发生。

引擎接管:挂限价单,不砸盘

以破产价接管,挂限价单到撮合慢慢平,不市价砸穿订单簿 —— 防连环爆(cascade)。

⭐ 部分减仓(依托分档表)

大仓位不一次全平,而是踩着风险限额分档表逐档减仓 —— 把仓位降到低一档、降低维持保证金要求,把账户救回安全区;不够再减一档,循环到安全或平光。

穿仓 → 保险基金 → ADL

亏损超本金(穿仓)由保险基金补;保险基金被击穿 → ADL 自动减仓。

⭐ ADL 自动减仓

极端行情兜底,强制减掉盈利方 + 高杠杆的对手仓填窟窿。排名 ≈ 盈利程度 × 杠杆(/保证金率),有排队亮灯。产品上靠透明度换信任(指示灯 + 事后说明)。

E · 风险限额

分档(也是部分减仓的依据)

仓位名义价值越大 → 要求 MMR 越高、最大杠杆越低。防巨鲸超高杠杆开超大仓、一爆击穿保险基金;体验上加大仓位时杠杆会被限,要提前提示。

F · 对冲(进阶,能拉开差距)

用户层对冲

用合约反向抵消现货风险,追求 delta 中性;成本是资金费率 + 基差风险 + 对冲腿自己也可能被强平。

⭐ 双向持仓 / 净敞口

同一合约可同时持多和空;净敞口 = 多头 − 空头(多 0.8 + 空 1 = 净空 0.2,盈亏按 0.2 算;但两条腿各占保证金、各有强平价)。

⭐ 对冲怎么赚钱

纯对冲不赚方向钱,赚非方向性收益 —— 最典型是资金费率套利(现货多 + 永续空,净敞口为零,吃正资金费),还有期现基差、跨期、跨所套利。风险在资金费率反转 + 某条腿被强平。

G · 周边但重要

订单簿:数量 vs 总数量

数量 = 单档挂单量;总数量 = 从盘口累加的累计深度 —— 用来估吃单深度 / 滑点。

⭐ 幂等

发奖 / 放币 / 赔付这类动钱操作必须做幂等 —— 同一操作调多次只生效一次,防网络重试、回调重复导致重复发 / 重复放的资损。

CFD 对照

做市商对赌型衍生品,对手方是 broker(B-book 下你亏它赚,有利益冲突);持仓成本是隔夜利息(付 broker),和永续"资金费率(用户互付、锚定价格)"形似神不同;受监管强(美国禁散户)。

术语

"水下" = 浮亏;"几个点"口语里通常 = 百分之几。

H · 高频"为什么"(面试爱问)

为什么用标记价?

防最新成交价被小资金插针操纵,导致一批用户被不公平强平。

穿仓谁承担?

保险基金 → 不够 → ADL。用户理想情况最多亏光本金,不倒欠。

强平提示怎么不打扰?

分层:持仓区常态色 → 接近维持保证金才主动 push → 强平前通知带追加保证金 / 减仓 / 平仓入口;阈值用历史数据校准。

三个核心项目故事 · 口语朗读版

OTC 卖币 王牌 · 主导 资金流转 0-1

我讲一个我从 0 主导的项目,OTC 卖币,就是让用户把手里的加密货币换成法币。

这个项目我做之前以为难点在流程,真正做进去才发现,最难的是 —— 钱到账这一环,平台其实不完全可控,因为法币打款是走第三方的。

用户最常反馈两个问题:一个是到账金额跟他预期对不上,一个是没按时到账。

我研究下来发现,金额对不上,其实大部分不是真亏了钱,是认知差。我们用的汇率是每天更新一次的、而且会比实时汇率略低一点,这个价差是平台正常的汇率风控。但用户会拿实时汇率去对,就觉得自己少拿了。所以我意识到,这本质是个预期管理的问题,不是赔付问题 —— 真正该做的,是在用户下单的时候就把成交汇率、预计到账金额讲清楚,让他一开始预期就对齐。

那确实是真损失的部分怎么办?这里当时有过争论,有人担心平台兜底会带来很大损失。我的判断不是不兜、也不是全兜,而是定一套有边界的兜底规则:差值在 0.1% 以内的,平台规则化赔付;超过阈值、或者异常的个案,才走人工复核。这样既让用户敢用,又把平台的损失敞口框在规则里。

状态设计上,我给用户做了确认收款和申诉两个出口。这里我特别注意一个边缘情况 —— 我没有把超时设计成"过了时间就自动一笔勾销",因为万一用户真没收到、又恰好没及时操作呢?所以确认和申诉的入口是一直保留、可追溯的。我的原则就是:涉及钱的事,绝不能让用户"过了时间就永远没法主张"。

结果上线后卖币的数据是不错的,不过具体数字是运营在跟。

这个项目给我最大的认知是:涉及用户资金、又有第三方的链路,兜底不是一句态度,是一道规则题 —— 可控范围内坚决兜底让用户信任,范围外用规则挡住平台损失。

合约体验优化 主力 · 参与 下单 / 持仓 / 数据展示

合约这块,我参与做了下单、持仓、资金费率、强平提示几个方向的体验优化。

先说清楚,我们是快速跟随型平台,这些能力头部平台基本都有、我们缺或者做得糙。所以我做的不是发明什么,而是 —— 对标币安、OKX,把我们缺的、体验差的一块块识别出来,判断优先级,再迭代补齐。比如下单原来只能按价值和数量,我补了按金额开仓的单位;字段太多用户看不懂,我用 hover 补说明、兼顾小白和专业用户;持仓区做信息分层,把强平价、保证金率这些风险字段顶出来。

但我觉得这里面最见功夫的不是"补什么",而是"落地做对"。这些东西抄进来不难,可很多细节抄错了就是事故 —— 比如强平价的精度和口径,风控算的和前端展示的对不上,用户就会觉得被提前强平、来投诉。所以我花了不少精力协同风控、研发把这些字段口径统一。

这个项目让我明白:做跟随型产品,产品经理的价值不在发明,而在 —— 选对该补什么、把落地细节做对、别抄错口径出事故,再持续迭代。

活动页配置化 加分 · 全负责 0-1 / 判断力

活动页配置化是我全部负责的一个项目。

背景是,我们早期搞活动有两种老办法都走不通。一种是跳转到第三方平台承接,但用户会有不信任感,而且数据存在第三方怕丢;另一种是让前端把页面写死,活动一常规化,每次定制开发就给技术带来巨大工作量。所以我推动把活动页做成可配置的,让运营自己就能搭。

这个项目最考验判断的,是哪些东西做成可配、哪些坚决不放开。比如发奖我就没有开放配置 —— 因为我们这阶段做不了自动发奖、风控也不健全,只能人工核实再发,我把它定义成过渡方案。原则是:不能为了灵活,把后台做得运营都不敢用、或者一配错就出资损。

最头疼的是任务模块怎么配进去。早期活动页就是展示规则加报名按钮。但上线后我发现一个问题 —— 用户感知特别弱,不知道自己完成了多少、离奖励还差多远,参与感很差。所以第二期我才把任务进度这些感知做进去。

任务配置真正复杂的地方,是多个任务组合起来还要考虑多语言。我的做法是每个文案按语言维度存,没配的 fallback 到英文兜底,组件做自适应,避免不同语言长度导致串版。

防配错这块我坦白讲,当时是"可编辑入口加运营自查",但这道防线其实不够 —— 人配错了自己再看往往也发现不了。如果再做一版,我会加发布前双人审核 + 关键字段二次确认,把防线从"事后能改"提前到"事前拦住"。

结果上线后数据不错,活动参与人数稳定,交易量也 ok。

这个项目让我明白:复杂产品不可能一蹴而就,先用最小版本跑通核心价值,再一步步加复杂度。 配置化的水平不在"能配多少",而在敢不敢划那条线 —— 80% 让运营自助,20% 留给人工和研发兜底。

王牌 · 主导0-1 · 接入 ChipPay
S情境

交易所此前没有 OTC 业务,缺少把数字资产换回法币的出金通道。我们从 0 接入,特意从最简单的"卖币"切入;实现上不自建支付承兑,而是接入第三方托管平台 ChipPay(由它匹配承兑商、托管、放币)。我开始前就预判到最大风险:钱走第三方,"到没到、到得对不对"平台并不完全可控 —— 整个设计都围绕"在不可控的第三方环节之上,兜住用户信任和资金安全"。

T任务

主导卖币能力接入落地,在保障资金安全、订单可追踪的前提下跑通核心链路,并在上线后基于真实反馈持续打磨出金体验。

A行动

一期 · 搭建

  • MVP 切入:先把"卖币"这一条链路跑通、打磨扎实,再往上扩展,不一次性铺满。
  • 接入 ChipPay、做状态映射:托管 / 匹配 / 放币由 ChipPay 负责;我做交易所侧下单流程(选支付宝 / 微信 / 银联收款、展示报价汇率与预计到账、确认收款),并对接接口和状态回调,把 ChipPay 的状态准确映射到我们的订单状态和用户提示。
  • 围绕预判风险做资金兜底:只有确认收款才放币;超时不做"自动一笔勾销",确认 / 申诉入口长期保留可追溯;异常分支当主角设计。

二期 · 上线后迭代

  • 金额对不上:查根因发现大多不是真损失,是汇率认知差(ChipPay 报价汇率略低于实时,用户拿实时汇率对)。判断为预期管理问题 —— 下单时就讲清成交汇率和预计到账;真损失才走有边界兜底(0.1% 内规则化赔付)。
  • 没按时到账:定位到是 ChipPay 承兑商匹配 / 打款排队。第三方速度不可控,但用状态透明化(展示"正在打款、预计到账"、超时主动触达)控住用户体感。
⇄关键取舍
  • 接入 vs 自建 —— 借 ChipPay 快速跑起来,精力放在能掌控、也最影响信任的地方。
  • 预期管理 vs 事后赔付 —— 从源头讲清汇率,减少申诉。
  • 兜底的边界 —— 0.1% 这条线同时兜住用户信任和平台损失。
R结果
  • 卖币能力从 0 安全上线,打通资产到法币出金闭环,上线后无资损事故。
  • 预期管理 + 状态透明,从源头减少两类高频困惑(具体数据由运营跟踪)。
  • 沉淀出对接第三方承兑通道的状态映射、异常处理、申诉兜底能力,为扩展其他 OTC 能力立稳地基。
✦洞察

接入型资金产品,价值不在"自己造了多少",而在"第三方不可控的那一环,你怎么用体验、透明度和兜底规则让用户依然信任平台";0→1 要先把最小核心链路跑扎实、上线,再靠真实反馈迭代。

◎可能被追问

为什么选 ChipPay?怎么评估第三方通道?

自建支付承兑太重太慢,接成熟通道能快速跑起来。评估看:承兑流动性与到账时效、汇率是否有竞争力、覆盖的收款方式、托管担保是否可靠、接口和状态回调是否完善、合规资质。

ChipPay 单点依赖,延迟甚至跑路怎么办?

短期靠状态透明 + 兜底 + 申诉兜住单笔;长期架构上把"承兑通道"抽象成可插拔的一层,预留接多通道、做分流和降级,不把身家绑在一家上。

状态回调丢了或和你们记录不一致?

不只依赖回调 —— 做主动轮询兜底 + 定时对账,不一致的进异常队列人工核查;放币、赔付这些动钱的动作做幂等,防重复处理。

兜底赔付的钱从哪出?会不会被恶意薅?

走平台风险预算,所以必须有 0.1% 的边界。防恶意:申诉要凭证支撑 + 人工复核 + 异常模式监控,和我设计其他异常防重复是一套思路。

为什么先做卖币,不先做买币?

卖币链路相对单向清晰,便于先把托管、放币、申诉、对账这套核心机制验证扎实,先把地基打牢再扩展,而不是一上来铺满。

合约交易体验优化

主力 · 参与下单 / 持仓 / 数据展示
S情境

合约机制复杂(杠杆、保证金、资金费率、强平……),用户理解门槛极高。我们作为快速跟随型平台,很多头部平台早有的体验能力,我们要么缺、要么做得糙,导致用户看不懂、决策效率低、客诉多。

T任务

参与合约体验优化,系统对标头部平台,把我们缺的、体验差的关键能力迭代补齐并优化落地,降低用户对交易参数、资金成本和仓位风险的理解成本。

A行动
  • 竞品对标,识别体验差距(价值起点):持续跟踪币安 / OKX / Bybit 的下单、持仓、资金费率、风控提示,梳理出"人家有、我们没有 / 做得差"的清单;对标不照抄,先搞懂每处为什么这么设计。
  • 判断优先级:差距一大堆、资源有限,按"用户痛点强度 + 影响面"排序,先补理解成本最高、最易引发误操作和客诉的。
  • 下单区迭代:补齐按金额开仓的单位(行业普遍有、我们只有价值 / 数量,用户要手动换算);梳理参数展示顺序,补触发价 / 委托价 / 成交价说明。
  • 持仓区信息分层:字段太多平铺抓不住重点,迭代成分层展示,突出强平价、保证金率、资金费率预计收付 —— 用户最该一眼看到"离爆仓多远、要付多少成本"。
  • 资金费率展示:针对"以为是手续费、不知结算时间"的误解,补上当前费率、结算倒计时、正负费率多空收付、预计成本。
  • 强平提示分层 + 自救出口:常态风险状态 → 保证金不足预警 → 强平前通知,每级把追加保证金 / 减仓 / 平仓入口放旁边。
  • hover 字段说明 + 落地把细节做对(最见功夫):用 hover 补说明兼顾两类用户;更关键的是协同风控 / 研发统一强平价精度、标记价、资金费率结算、保证金率阈值等口径 —— 抄错一个,页面强平价和实际触发价对不上,就是事故。补进来不难,做对才难。
⇄关键取舍
  • 补什么 / 不补什么:资源有限,按痛点和影响面排优先级,不是看见竞品有就抄。
  • 照搬 vs 做对:范式对齐行业降学习成本,但结合自己的用户、风控、字段口径把落地做对 —— 尤其口径,抄错就是事故。
R结果
  • 迭代补齐并优化了下单、持仓、资金费率、强平提示等核心场景,降低理解成本、缩小了和头部平台的体验差距(具体数据由数据团队跟踪)。
  • 推动关键字段展示与计算口径规范化,减少后续需求的口径沟通成本。
✦洞察

做跟随型产品,PM 的价值不在发明,而在:选对该补什么(差距识别 + 优先级)、把落地细节做对(结合自己的用户和风控,别抄错口径出事故)、并持续迭代。会判断"抄什么、怎么落地",本身就是产品能力。

◎可能被追问

交易所是移动端为主,hover 在手机上不存在,怎么办?

hover 是桌面端形态,移动端我用点击信息图标 / tap 展开,逻辑一样。核心不是"hover"这个控件,而是"信息按需展开、默认不打扰"这个原则,它在两端有不同落地形态。

既然全是别人也有的,你的价值到底在哪?

价值不在发明,在差距识别 + 优先级判断 + 落地质量:决定补什么、先补什么,以及把口径这种细节做对 —— 抄错强平价口径就是事故,做对才是真本事。

新增开仓单位,有人真用吗?怎么验证是真需求?

具体使用数据是运营在跟,我没拿到。但需求来源不是拍脑袋 —— 来自客服反馈里"想按金额开仓要自己换算"这个真实痛点,且是行业普遍做法。有数据我会看使用占比验证。

口径统一,举个你和风控真吵过的例子?

强平价的精度和口径:风控用完整精度,前端原样展示读不了、自己取整又会和实际触发价对不上引发投诉。最后定"展示精度跟随合约、标注预估价以实际为准、取整偏保守"。

持仓字段那么多,凭什么决定哪个突出?

按"用户决策和风险感知优先级":强平价、保证金率、盈亏最该一眼看到,其余弱化。

强平提示做太多,会不会打扰、用户麻木?

会,所以分层 —— 只有接近维持保证金才主动触达,阈值和风控用历史强平数据校准,避免正常波动就报警。

活动页配置化搭建

加分 · 全负责0-1 · 判断力
S情境

平台活动频次持续攀升,早期两种承接方式都撑不住:跳转第三方带来用户不信任 + 数据丢失风险;前端写死页面在活动常规化后给技术带来大量重复开发,拖慢上线节奏。

T任务

全权负责,把活动页从"定制开发"转型为"配置化搭建",建设统一、可复用、可控的搭建能力,让运营自助快速上线不同类型活动。

A行动
  • 抽象通用组件:Banner、活动规则、任务、奖励、排行榜、进度条、弹窗等,形成可复用组件体系。
  • 划清可配边界(核心判断):高频通用低风险的开放可配;一次性玩法留给研发;发奖不开放 —— 平台还做不了自动发奖、风控不健全,走人工核实,定义为过渡方案。原则:绝不为灵活把后台做成运营不敢用、一配错就资损的"半成品开发工具"。
  • 分期迭代:一期先做展示 + 报名;上线后发现用户感知弱(不知道自己完成了多少),二期才补上任务进度感知。
  • 解决多语言:文案按语言维度存储,缺失 fallback 英文,组件自适应防串版。
  • 建搭建流程与权限:创建 / 配置 / 预览 / 发布 / 下线全流程 + 审核机制。
⇄取舍与诚实复盘
  • 灵活 vs 可控 —— 克制地划"80% 自助、20% 兜底"的线。
  • 防配错(坦白):当时其实没做发布前审核、预览也是发布后的,靠运营自查发现问题再改,这道防线不够;唯一的防护是标准化组件挡住了"丑",但挡不住"错 / 不合规"。更稳的应是发布前预览 + 审核、高风险字段双人过,把防线从"事后能改"前移到"事前拦住"。
R结果
  • 建立配置化搭建能力,支持多类型活动快速落地。
  • 常规活动运营基本可自助、显著降低对研发定制的依赖、上线效率提升(这才是该看的成功指标,比"参与人数"更能说明价值)。
  • 沉淀活动组件与配置规范,减少重复沟通和开发。
✦洞察

复杂产品不可能一蹴而就,先用最小版本跑通核心价值再加复杂度;配置化的水平不在"能配多少",而在敢不敢划那条线 —— 克制,有时候比灵活更难。

◎可能被追问

发奖走人工,活动量一大不就成瓶颈了?

会,所以我明确把它定义成过渡方案 —— 现阶段活动量人工能覆盖,是权衡后的选择;等自动发奖能力和风控成熟,这个口子规划要逐步打开。

多语言文案谁翻译?质量谁保证?

我在产品上保证的是结构支持多语言(按语言维度存)、缺配 fallback 英文、不串版;翻译本身由内容侧提供、靠内容流程把关 —— 不该由配置系统兜,这是我划的职责边界。

运营配出一个很丑、信息错误、甚至不合规的活动页怎么办?

坦白讲这块防线不够 —— 当时没做发布前审核、预览也是发布后的,靠运营自查发现再改。唯一防护是标准化组件挡住了"丑",挡不住"错 / 不合规"。这是我复盘最想补的:发布前预览 + 审核、高风险字段双人过。

现有组件配不出运营要的新玩法怎么办?

先判断这玩法的频率和复用性:高频可能复用的纳入组件;一次性特殊玩法走研发定制。我做过一次 —— 把复杂玩法拆开,高频部分配置化、特定动态逻辑单独给研发,两边都满足。

06

交易机制问答

这份 JD 的重头戏,必背。答出"机制 + 产品该怎么呈现"两层,别只背定义。

强平 · 触发与执行

讲讲强平是怎么触发和执行的?

当仓位保证金率跌到维持保证金率就触发。关键是用标记价格算、不是最新成交价,防止插针把价格瞬间打穿、误伤一批用户。触发后强平引擎接管仓位,通常挂限价单到撮合系统慢慢平,而不是市价砸盘 —— 避免大单击穿订单簿引发连环爆。平得好的盈余进保险基金,穿仓了保险基金补,再不够就 ADL 自动减仓。

全仓 vs 逐仓

全仓和逐仓的区别?产品上最该讲清楚什么?

逐仓每个仓保证金独立,最多亏这个仓的本金;全仓共享账户余额,更扛波动但爆仓可能亏更多。产品上最该讲的不是定义,是后果 —— 用户切换模式时,直接告诉他强平价和最大亏损发生了什么变化,让他基于后果选择,而不是记名词。

资金费率

资金费率是什么?它的作用?

很多用户以为是平台收的手续费,其实是多空之间互付,平台不收这笔钱。它的本质作用是把永续价格锚定到现货指数价 —— 永续溢价时费率为正、多头付空头,惩罚做多、把价格拉回现货。我做过资金费率展示优化,重点是把收付方向、结算倒计时、预计成本讲清楚。

标记价格

标记价格为什么要存在?

如果直接用最新成交价算强平和盈亏,深度差的合约很容易被小资金插针打穿、触发一批不公平的强平。所以用标记价 —— 基于指数价加合理基差算出来的、更平滑公允的价格 —— 算盈亏和触发强平,成交才用最新价。产品上要标注清楚哪个价用于成交、哪个用于强平,不然用户会困惑"还没到强平价怎么就爆了"。

ADL 自动减仓

ADL 是什么?怎么降低用户负面感受?

强平的最后防线 —— 极端行情下保险基金被击穿时,系统强制减掉盈利方、高杠杆的仓位来平掉穿仓窟窿。用户最不满"我在赚钱凭什么动我",所以产品上要透明化:持仓区放 ADL 排队指示灯让他提前看到风险、事前教育、事后清楚说明。本质是用透明度换信任。

风险限额

风险限额是干嘛的?怎么影响体验?

仓位越大平台承担的强平风险越高,所以分档要求更高的维持保证金、更低的最大杠杆。它会让用户加大仓位时突然发现杠杆变小或加不上仓。产品上要在接近档位边界时提前提示"继续加仓需要降低杠杆",让限制可解释、可预期。

强平前提示

强平前你会怎么做风险提示?

分层,而且每一级都带自救出口。 持仓区常态展示保证金率、颜色分档;接近维持保证金时主动 push 预警;强平前最后通知,并把追加保证金、减仓、平仓的入口直接放在提示旁边。目的不是免责声明,是真在被强平前给用户自救机会。阈值要和风控用历史数据校准,避免正常波动就疯狂报警。

07

追问预案

顺着故事最可能被追的地方,提前背好。

你项目大多没有硬数据,怎么证明价值?

有些最终数据是运营和数据团队在跟,我没拿到精确数字,这我不会编。但我能讲可观察的变化 —— 某类客诉明显少了、活动不用研发定制了;更重要的是我能讲清过程里的判断和取舍,这些是我亲手做的。判断力比背一个 KPI 数字更能说明一个产品经理的水平。

方向都是领导定的,你的价值在哪?

方向是团队定的,但怎么落地是我推的。同一个方向可以做得很糙也可以很稳,区别就在有没有人去拆真问题、定原则、把异常想透、和风控研发对齐口径。像 OTC 的兜底规则、配置化里发奖不开放,这些落地判断都是我自己拍的。

讲一个失败的项目。

DigiFinex 活动页改版。熊市想靠改版拉活跃,我花大精力打磨交互,结果远低于预期。复盘发现两个我的错:把体验当成主要矛盾,但真正天花板是行情;精力全在交互上,但用户其实嫌奖励不够。之后我养成习惯 —— 做事前先问"这事的瓶颈到底是体验、激励还是大盘",别用埋头优化掩盖方向错判。

OTC 的"可控范围"到底怎么定?

规则化,不靠感觉。差值在 0.1% 以内系统判定可赔付、走快速流程;只有超阈值或异常个案才人工复核。0.1% 这条线是结合历史汇率波动和第三方误差定的,不是拍脑袋。

活动配置化,参与人数稳定跟你做配置化有什么关系?怎么证明项目成功?

您问得对,参与人数不是衡量这个项目的好指标,那更多是运营和行情决定的。这个项目该看的是初衷有没有达成 —— 运营能不能自助搭活动、不再占研发排期。从这个角度它是成功的:常规活动基本不用研发定制,上线效率明显提升。

A · 衍生品设计与迭代 ★

你做过哪些衍生品相关的产品工作?最有代表性的是什么?

我讲最有代表性的 —— 强平价展示口径的统一。背景是用户投诉"App 显示的强平价还没到,仓位就被强平了"。排查下来不是引擎算错,是口径不一致:触发用标记价格,有的端展示参考价却用最新成交价,行情剧烈时两个价差出一截,用户按页面显示扛单、实际提前被强平。

  • 全链路对齐:把触发口径、展示口径、推送提醒口径梳理一遍,拉着研发逐端对齐到标记价格。
  • 投诉转教育:强平价旁加口径说明 —— "为什么用标记价格:最新成交价可能被瞬间插针,用标记价是保护你不被误伤"。
  • 机制沉淀:把口径类问题建清单,后续排期默认最高优先级。

合约产品 80% 的迭代都是这种正确性问题 —— 不产生新收入,但做错一个就是资损和信任事故。判断一个人懂不懂合约产品,看他敬不敬畏这类细节。

◎ 追问:标记价格怎么算的?

一般取多家主流交易所现货价格的加权指数,加上基差的移动平均,目的是平滑、难被单一市场操纵。具体加权规则各家有差异,这块底层细节我还在深入。

A · 季度规划 ★

如果让你规划下一个季度的衍生品迭代,你怎么定方向?

先说句实话:在上家,大方向是业务负责人定的,但方向下面的问题清单和优先级是我拆的。我的输入源有三个:

  • 客诉/工单聚类:最真实的痛点来源 —— 强平相关客诉持续排第一,说明强平透明度和预警有欠账。
  • 竞品差距清单:持续维护一张表,头部所有、我们没有的能力,按"影不影响交易决策"排序 —— 风险限额分档展示排前,纯视觉优化排后。
  • 运营侧能力需求:下季度要打什么活动、缺什么能力,提前收进来,不然全是插队需求。

排序原则固定:资金安全和口径正确 > 主链路转化卡点 > 体验优化;再留约 20% 余量给行情驱动的临时需求 —— 排满了整个季度计划都会崩。

A · 永续 vs 交割

永续合约和交割合约的产品差异?

核心差异一个:永续没有到期日,所以需要资金费率让价格锚定现货 —— 多空互付,价格高于现货时多头付空头压价回落;这里很多人搞错:这笔钱平台不收,是用户间的转移支付。交割有到期日靠交割收敛,无资金费率但有基差。

落到产品上:永续要做资金费率的展示、历史、下期预测(费率直接影响持仓成本,重仓用户极敏感);交割要做到期提醒、移仓/展期引导,用户忘了到期被动交割就是大量客诉。用户结构上永续是绝对主流,资源投放按这个比例来。

A · 新品类 0-1

如果我们要上一个新的衍生品品类(比如期权),你怎么从 0 开始?

先坦白:期权我没做过。但我完整做过一个业务的从 0 到 1 —— OTC 卖币,讲讲那套方法怎么迁移:

  • 先答"做不做"再答"怎么做":看头部所的期权形态、交易量占比、用户结构,关键是判断存量用户和期权用户画像的重合度 —— 短线高杠杆散户为主的话,简化版涨跌期权可能比标准期权更对路。这个判断错了,后面做得再好都没用。
  • 砍出最小闭环:当年 OTC 先只做卖币 —— 链路最短、风险最小。期权同理:先上买方单腿(买 Call/Put,最大亏损=权利金、教育成本最低),卖方收保证金、有无限亏损风险,和组合策略全部后置。
  • 风险展示做成一等公民:衍生品新品最大的坑不是功能缺失,是用户不理解自己承担什么风险 —— 下单页最大亏损、盈亏平衡点、到期时间必须比"预期收益"更醒目。
  • 上线前过异常清单:标的剧烈波动的定价、流动性不足的处理、到期结算边缘情况。

主流程谁都画得出来,产品经理的价值在异常态 —— 这是 OTC 教我的。

B · 行业调研 ★

你做过什么行业调研?怎么落地成产品的?

讲数值精度的竞品调研。起因是同一币对在不同页面小数位不一致 —— K线一个精度、下单框一个、订单记录又一个,用户会怀疑"数据是不是有问题"。我的调研分三层:

  • 拉规则表:头部几家所的价格/数量/金额精度,分别在什么页面用什么位数。
  • 搞懂"为什么":这才是调研的价值 —— 价格精度背后是最小变动价位(tick size),和币的价格量级、市场深度有关;数量精度背后是最小下单单位,关系到小额用户能不能交易。
  • 产出规范并落成配置:每个场景什么口径、四舍五入还是截断(资产页往上进位一分钱,累计就是资损);做成研发直接照抄的配置表而不是文档,上新币对不需要再人为判断。

抄表格是执行,搞懂"为什么"才是调研 —— 只抄结论,别人的规则换个市场环境就不适用了。

B · 数据决策 ★(戳软肋)

举一个你根据数据调整产品的例子。

先老实说明前提:上家的数据基建有限,没有完整埋点和 BI,所以我形成了一套方法 —— "可观察变化 + 老实标注的估算"。举活动配置化的例子:

  • 可直接观察:运营从依赖研发排期(以天计)变成当天自助搭活动;研发在活动上的介入次数趋近于零 —— 不需要埋点,看工作流就能确认。
  • 老实标注的估算:交易侧带动给估算并明确口径 —— 参与人数多少、按历史转化比例估带来多少,同时说清"这是估算,置信度中等"。

宁可给标注清楚的估算,不给看起来精确的假数字 —— 决策错了可以调,数据造假污染决策依据,后面全错。也正因此,JD 里"根据运营数据调整产品"对我反而是吸引力:意味着贵司数据基建完整,我的分析习惯终于有完整弹药。

◎ 追问:那你到底用数据做过决策吗?

做过,只是颗粒度粗。客诉工单的分类统计就是数据 —— 强平类客诉长期占比最高,直接决定我把口径统一排最前。数据不一定是埋点漏斗,能支撑决策的事实都是数据。

B · SQL / 数据能力 ⚠️面前填实

你会 SQL 吗?数据能力到什么程度?

(按真实水平答,模板:)SQL 能独立完成日常取数 —— 查活动数据、拉转化漏斗、分群对比,多表关联没问题;窗口函数会用但不算熟练。Excel 透视和 ROI 测算是日常工具。Python 数据分析不会,在补。

C · 年限短板 ★

我们希望 5 年经验,你才 3 年,怎么看?

我不跟年限辩,说说这 3 年的密度。衡量经验的关键是独立决策的次数,不是坐在岗位上的时间。我有两段"决策密度"高的经历:

  • OTC 从 0 到 1:调研、选型对接第三方承兑、订单状态机、"钱对不上怎么赔"的兜底规则 —— 每个决策都是我拍的,没有前人方案可抄。
  • 合约链路迭代:资损敏感环境,强平价口径改错一个字段就是事故 —— 逼我形成对正确性和边缘场景的敬畏,这个有人做 5 年纯功能迭代也未必建立。

也承认差距:老手见过的周期和事故更多。我的弥补方式是把每次决策当成压缩经验的机会 —— 包括决策错的时候,比如配置化一期没做发布审核,这个坑我现在讲得出完整改进方案,就因为踩过。

C · 证券背景

没有股票/证券背景,怎么补?

分两层。机制层同源可迁移:合约保证金对应两融/期货保证金,强平对应券商强制平仓,杠杆、全仓逐仓在两融里都有影子;资金费率虽是加密原生,但它解决的"衍生品锚定现货"问题,传统市场靠交割和套利解决 —— 底层金融逻辑是一套,切换成本在术语和惯例。

真正差的是监管和业务惯例:T+1、涨跌停、投资者适当性管理,这些是加密没有的约束,产品设计必须绕着走。我在系统补,方式是看券商 App 的产品设计倒推背后的监管要求。
