01需求分析

1.1 需求背景

平台上线美股代币（xStocks 系列，如 INTCX / NVDAX / GOOGLX）后，交易对在列表与交易页仅展示交易代码（ticker）与英文全称。中文区用户普遍不认识 INTCX 即「英特尔」、NVDAX 即「英伟达」，直接影响资产识别与交易转化。

现有中台「编辑币种」仅提供「名称（交易代码）」与「全称」两个名称字段，且实际运营中「全称」常被误填为交易代码本身（如 GOOGLX 的全称也填成 GOOGLX），既无中文名，也无任何多语言能力。前端因此出现「同一个币在列表有名、在交易页空白」「有的币有中文名、有的没有」等不一致现象。

本需求为币种建立多语言名称体系：由中台按币种维护各语言展示名，前端按用户语言展示，缺失时按统一兜底链回退，覆盖全站所有展示币种名的场景。

需求来源　群内讨论中，需求方最初提出「后端加一个标识、前端展示」；PM 提出「做多语言名称会更好，标识可另作他用」；需求方最终确认「参考竞品出方案，大交易所都有做」。经竞品调研，结论为名称与标识是两套并行系统，本需求聚焦「多语言名称」。

1.2 用户分析

用户类型特征描述核心诉求产品对应机制
中文区用户主力人群，不熟悉美股代币英文 ticker一眼看懂这是哪家公司 / 哪个资产按简体中文展示币种名（英特尔、英伟达）
繁体 / 多语言用户港澳台及日韩等地区用户用本地语言识别资产按用户语言取对应名称，缺失回退
英文 / 国际用户习惯以英文全称或 ticker 识别维持现有英文展示不变英文名即「全称」，展示逻辑不变
运营人员负责币种上架与信息维护批量、高效维护各语言名称，改一处全站生效中台集中配置，前端统一取名

1.3 竞品分析

主流交易所均已实现币种多语言名称，且普遍将「名称」与「分类标识」作为两套独立系统并行维护。核心做法一致：按币种维护一份多语言名称字典，前端按语言取名，缺失时回退英文全称。

交易所币种名称机制（本地化）美股代币展示
OKX多语言名称覆盖较全，中文站较多币显示中文名，按语言取展示名ticker 下挂中文 / 公司名，另有「板块」标签独立分类
Bybit每资产带本地化名称，中文站显示公司中文名AAPLx + 「Apple / 苹果」，Tokenized Stocks 专区独立
Gate多语言名称字典，中文站显示中文名ticker + 公司中文名，美股代币专区分类
Binance以 ticker + 英文全称为主，少数主流币有中文；标签体系强现无 xStocks；分类靠板块 / 标签
Kraken名称以英文为主（欧美用户为主）AAPLx + 「Apple xStock」
结论　① 采用「按币种维护多语言名称字典 + 前端按语言取名 + 缺失兜底」的主流机制；② 名称（英特尔）解决「看懂」，标识（美股板块）解决「归类/筛选」，二者不冲突、不互相替代；③ 本需求只做名称，标识沿用现有《市场分类配置中心》，不在本文档范围内。

02产品概述

2.1 产品逻辑

整体链路为「中台配置 → 前端按用户语言取名 → 未配置回退英文」。前端在任一展示币种名的位置，按下方状态机决定第二行展示内容：配置了当前语言就展示该语言名称，未配置则展示英文全称。英文全称为必填项，因此第二行始终有值，不存在空白或不展示的情况。

第二行完整格式　第二行 =（上图取到的）名称 + 成交额，展示为「名称 | 成交额」，例：Tutorial | 6,359.38万。本图仅描述名称部分的取值逻辑；成交额为既有行情数据，恒定展示，不属本需求范围。

2.2 功能架构

能力由三层构成，数据单向流动，前端不自行拼名。

层模块职责
中台配置层编辑币种 · 多语言名称按币种维护各语言展示名（可增删语言）、维护英文全称（兜底 / 默认名）；语言种类来自平台支持语言，不逐币新造
下发层币种 / 行情 / 交易对信息向前端提供当前用户语言下的展示名与英文全称，供前端取名与兜底
展示层App / Web / H5 各页面所有出现币种名的位置统一取同一份名称、走同一兜底链，三端口径一致
与「分类标识」的边界　美股 / TradFi 等分类标签由现有《市场分类配置中心》（标签字典 + 分类配置）维护，与本能力解耦。前端一个位置可同时展示「多语言名称」与「分类标识」，但二者取自不同系统。

2.3 术语解释

术语含义
名称（交易代码）币种的唯一交易标识 / Symbol，如 BTC、GOOGLX。前端第一行主体，不参与本地化。
全称币种的英文名 / 默认名，如 Bitcoin、Alphabet。既是英文用户看到的名，也是所有语言的兜底值。
多语言名称某币种在各语言下的展示名字典，如 zh-CN:比特币、zh-TW:比特幣。前端第二行按用户语言取值。
兜底链取名的回退顺序：当前语言名称（多语言，可选）→ 英文全称（必填，始终有值）。英文全称必填，故第二行始终有值，无隐藏情况。
分类标识币种的归类标签（如「美股」），用于筛选与运营专区，独立于名称，由市场分类配置中心维护。

2.4 重要信息 Checklist

✅ 名称按币种维护，交易对（NVDAX/USDT、NVDAX/USDC）自动复用同一 base 名称
✅ 第二行展示格式为「名称 | 成交额」（如 Tutorial | 6,359.38万），名称部分取多语言值、成交额为既有数据
✅ 兜底链为「当前语言名称 → 英文全称」，英文全称为必填项，第二行始终有值，永不空白、不会不展示
✅ 英文名统一在「全称」维护，多语言列表不单列 English，避免重复填写与不一致
✅ 多语言名称全部非必填（含简体中文），未配即走兜底；简中留空仅软提示，不硬拦截
✅ 全站三端（App / Web / H5）取同一份名称、同一兜底链，口径一致
✅ 「兜底」为后台机制，前端对用户静默，不展示「·兜底」等内部术语

2.5 上线节奏

阶段范围说明

3.2 页面交互流程

中台配置流程

运营进入「编辑币种」→ 维护「全称」（英文 / 默认名）→ 在「多语言名称」区块按语言填写展示名，可「＋ 添加语言」补充或「×」移除某语言 → 保存生效。语言种类来自平台支持语言，不可在此新造。

前端展示流程

用户打开任一含币种名的页面 → 客户端携当前语言请求 → 按图 A 状态机取名：命中该语言名称则展示，未配置则展示英文全称（必填，始终有值）→ 用户切换语言后同一逻辑重新取名，三端表现一致。

3.3 原型及说明

以下贴图取自《后台前端联动原型 v1》，配合 MECE 文字说明拆解页面逻辑。

① 中台 · 编辑币种（多语言名称区块）

  • 名称：交易代码，只读展示，不参与本地化。
  • 全称：英文 / 默认名，英文用户与未配语言用户都取它；作兜底层。
  • 多语言名称区块：逐语言一行「语言 + 名称输入 + 删除」；「＋ 添加语言」仅从平台已开通语言中挑选补行。
  • 非必填：所有语言（含简中）均可留空 / 删除，留空即走兜底；简中留空仅软提示。

② 前端 · App / Web 展示

  • 第一行：交易代码 + 计价币（INTCX/USDT），不变。
  • 第二行：格式为「名称 | 成交额」（如 Tutorial | 6,359.38万）。名称部分按用户语言取值，未配置则展示英文全称；成交额为既有行情数据。
  • 静默兜底：对用户仅展示干净名称，不出现「·兜底」等内部标记。
  • 三端一致：App / Web / H5 取同一份名称与兜底链。

3.4 边界 Case

#场景预期表现
B1某语言名称未配置展示英文全称（英文为必填，始终有值），前端不提示兜底
B2用户语言为英文展示英文全称，视为正解
B3简体中文留空保存允许保存，仅软提示；中文用户展示英文全称
B4同 base 多交易对NVDAX/USDT 与 NVDAX/USDC 复用同一 base 名称，配一次全生效
B5删除某已配语言该币该语言名称清空，此后展示英文全称
B6名称含超长 / 特殊字符前端第二行单行截断省略；输入长度上限 数值待确认（Q-03）
B7平台新增一门语言由语言管理全局开通后，各币种多出一行待填，覆盖口径一致
B8币种下架展示名随币种可见性收起，配置数据保留
英文全称为必填项　是取名的最终兜底，因此第二行始终有值——产品中不存在「空白 / 不显示第二行」的情况；未配置某语言时一律回退英文，只有配置了该语言才切换成该语言名称。

05API 相关调整

本章为唯一允许出现实现层内容的章节。以下为方向性说明，最终以研发接口设计为准。

5.1 C 端接口

  • 币种 / 行情 / 交易对相关接口，在币种信息中增加当前语言展示名与英文全称两项返回；建议服务端按请求语言直接下发单值展示名，缺失时由服务端按兜底链回退，前端仅负责渲染（第二行始终有值）。
  • 兜底链在服务端实现，保证 App / Web / H5 三端口径统一，避免各端各自兜底导致不一致。

5.2 管理后台接口

  • 编辑币种接口增加多语言名称的读写：按币种维护「语言 → 名称」映射，支持新增 / 修改 / 删除某语言项。
  • 可选语言列表取自平台支持语言配置，后台不新造语言。
  • 如 Q-04 确认需审核，则增加名称变更的审核 / 操作日志能力。

5.3 缓存与生效

  • 币种名称属低频变更、高频读取数据，建议接入缓存；保存后需有明确的缓存刷新机制，保证配置改动及时全站生效。
