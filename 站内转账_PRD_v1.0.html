01需求分析

1.1 用户分析

目标用户：平台已注册并完成登录的用户。

核心场景：用户需向平台内其他用户转移资产，典型如朋友间 AA、借还款、社群/团队打款等，且希望免手续费、实时到账、无需填写链上地址。

用户痛点：

  • 走链上提现需选择网络、填写地址、支付网络手续费、等待区块确认；
  • 链上地址一旦填错，资产不可逆丢失，操作门槛与风险较高。

产品价值：以「仅凭对方 UID、免费、实时」的方式完成站内资金流转，降低操作成本与出错风险，提升平台内资金流转效率与用户黏性，沉淀站内资金。

1.2 竞品分析

【待补充】——本次需求未开展竞品调研。后续如需，可补充主流交易所站内转账/支付类产品（如币安 Pay、OKX 内部转账等）的对比分析。

02产品概述

2.1 产品逻辑

2.1.1 主流程

资产页 · 提现→ 选内部转账→ 输 UID / 金额 / 留言→ 确认并验证→ 强原子执行→ 结果 · 记录
环节用户动作系统行为
入口资产页点「提现」→ 选「内部转账」App 弹出方式选择弹窗；Web 以 Tab 区分
发起输入收款人 UID / 数量 / 留言实时校验 UID 是否存在、余额是否充足
确认验证核对摘要 + 输入验证码校验邮箱验证码（及 2FA）
执行点击确认转账强原子执行：扣款 + 入账，同成同败
结果查看结果成功即时到账 / 失败整体回滚未扣款

2.1.2 订单状态机

  • 前置拦截（余额不足 / UID 不存在）：发起页提交前阻断，不生成订单。
  • 处理中：原子事务执行中（实时，通常极短暂）。
  • 成功：扣款腿与入账腿均成功，资产实时到账。
  • 失败：系统异常/网络超时，整体回滚，用户未扣款。

说明：因账务强原子，系统不存在「已扣未入」中间态。

2.2 功能架构

  • C 端：提现入口区分 / 内部转账发起 / 安全验证 / 转账结果 / 转账记录 / 收付双视角详情。
  • 管理后台：转账流水查询 / 状态监控（成功 · 处理中 · 失败），仅查询监控，无人工补账处置。

2.3 术语解释

术语解释
站内转账平台内用户之间的资金划转，不上链、实时到账、免手续费。
UID平台用户唯一标识，内部转账收款人的唯一识别方式。
扣款腿 / 入账腿一笔转账中「付款方扣款」与「收款方入账」两个动作。
强原子扣款腿与入账腿同成同败，绝不出现「已扣未入」。
2FA身份验证器（如 Google Authenticator）生成的动态验证码。
前置拦截在发起页提交前即校验并阻断（如余额不足、UID 不存在），不生成订单。

2.4 重要信息 Checklist

项结论
手续费不收取，收款方到账金额 = 付款方转账数量
到账时效实时到账
可否撤销不可撤销，无撤销/退回功能
收款人识别仅支持 UID
名称展示全流程只显 UID，不展示昵称/实名
限额不做限额（单笔/单日均不限）
KYC不做 KYC 验证
风控拦截当前版本不做

2.5 上线节奏

  • 一期：内部转账（本文档范围）。
  • 链上提现：入口已与内部转账并列展示，其具体流程不在本次需求范围内。

05API 相关调整

本章为唯一涉及实现层的章节，说明接口变动方向（非完整接口定义）。

  • UID 存在性校验接口（新增）：供发起页实时校验收款人 UID 是否存在，仅返回是否有效，不返回名称等敏感信息。
  • 发起内部转账接口（新增）：以强原子事务完成「扣款 + 入账」，保证同成同败；需支持幂等，防重复提交。
  • 邮箱验证码发送 / 校验接口（新增或复用）：发送邮箱验证码；提交时校验邮箱码，已绑 2FA 用户同时校验 2FA。
  • 转账记录列表接口（新增）：仅返回成功记录，区分转出/转入；按当前登录态鉴权，只返回登录账号自己的记录，不接受传任意 UID 查询他人记录（防横向越权）。
  • 转账详情接口（新增）：按视角返回转出/转入详情；同样按登录态鉴权，校验该订单归属当前账号。
  • 账号隔离与登出清理：转账相关数据严格绑定当前登录账号；退出登录时客户端须清除上一账号本地缓存（记录/余额/草稿等），避免账号切换后数据残留。
  • 管理后台流水查询接口（新增）：支持按订单号、UID、状态、时间查询全部状态流水；返回双腿状态。
  • 账务一致性保障：扣款与入账须在同一事务/分布式事务内，失败整体回滚，杜绝「已扣未入」。
